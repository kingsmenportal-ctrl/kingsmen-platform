## 1. Original meaning preserved

Number 9 means Jarvis must not live as a plain chatbox. Jarvis must have a full visual command cockpit. The Commander must be able to see Jarvis, not only read replies.

Jarvis must feel like a private Kingsmen Command House interface: dark, cinematic, structured, alive, serious, and operational. The HUD must show voice state, conversation, strategy, agents, tools, evidence, memory, command queue, system pulse, risks, approvals, and recommended next actions.

The HUD is not decoration. The HUD is part of the intelligence layer. It tells the Commander what Jarvis is doing, what evidence exists, what is still missing, which agents are active, which tools are being routed, which action needs approval, and whether Jarvis is speaking from memory, repo proof, live verification, internal truth, or provisional evidence.

Jarvis must never be reduced to:

- a white chat page,
- a plain prompt box,
- a black-and-white admin panel,
- a broken card layout,
- a generic SaaS dashboard,
- a public chatbot widget,
- a simple command input,
- a static report page,
- a button-only control panel.

Number 9 locks the visual body of Jarvis.

## 2. Conversational role

The HUD must support conversation, not only commands.

When the Commander talks to Jarvis, the HUD must show the active conversation stream, current context, mode, and recommended next action. The Commander must be able to have a natural discussion while seeing supporting panels.

The conversation surface must allow:

- typed dialogue,
- voice dialogue,
- long-form strategy discussion,
- debate threads,
- clarification questions,
- correction handling,
- file/repo/source references,
- follow-up continuity,
- evidence drawer access,
- approval prompts.

The HUD must not force every conversation into a button or rigid workflow. The Commander must be able to speak naturally and see Jarvis organise the conversation visually.

Example: if the Commander says "Jarvis, talk me through why this plan is weak", the HUD must show Debate Mode, option cards, risk cards, source confidence, and recommended command.

## 3. Dialogue and debate role

The HUD must make debate visible.

Jarvis must not only debate in text. It must show:

- strongest argument for,
- strongest argument against,
- weak assumptions,
- evidence level,
- doctrine conflicts,
- cost/risk,
- operational impact,
- recommended command,
- Commander decision required.

Debate Mode should visually separate:

- Option A,
- Option B,
- Option C,
- risks,
- dependencies,
- evidence gaps,
- no-useless-layer warning,
- Commander decision point.

If Jarvis disagrees with the Commander, the HUD must show why. Disagreement must be evidence-led and visual, not hidden inside a paragraph.

## 4. Strategy and planning role

The HUD must support strategic planning.

Strategy requires more than a reply. Jarvis must visually organise plans into phases, dependencies, blockers, proof required, risk, cost, workload, and next command.

Strategic HUD panels must include:

- objective panel,
- current position panel,
- locked doctrine panel,
- planned vs built vs proven status,
- dependency map,
- blocker map,
- risk register,
- recommended sequence,
- proof required,
- Commander decision required.

For Kingsmen, the HUD must show the difference between doctrine, repo file, runtime proof, and production readiness. It must not visually imply readiness when proof is missing.

## 5. Voice-wake and spoken interaction role

The HUD must show voice activity.

Voice wake must be visual. When the Commander says "Jarvis", the HUD must change state: sleeping to wake detected, then listening, transcribing, thinking, speaking, or awaiting approval.

Voice HUD elements:

- central Jarvis orb,
- waveform,
- wake pulse,
- listening indicator,
- transcript preview,
- confidence/ambiguity notice,
- speaking state,
- blocked voice command notice,
- approval-required notice.

Voice must never be invisible. The Commander must see whether Jarvis heard correctly and whether the spoken instruction is safe to continue.

If the transcript is unclear, HUD must show: "Spoken instruction unclear — confirmation required."

If the voice command is risky, HUD must show: "Commander approval required before execution."
