# NUMBER 11A — COMMANDER CORRECTION: LOVABLE MUST ALREADY BE AVAILABLE LIKE OTHER APPS

Status: LOCKED
Owner: Commander
Scope: Amendment to Number 11, not Number 12
Source basis: Commander correction after Number 11, Lovable connector boundary, Jarvis Agent Tool Routing, Full Visual HUD Command Cockpit

## 1. Correction locked

The Commander correction is:

"Lovable must already be available like other apps."

This correction does not cancel Number 11. It strengthens it.

Number 11 already placed Lovable under controlled UI prototyping and not source of truth. However, the exact availability rule was not strong enough. The Commander is correcting that now.

The final lock is:

- Lovable must appear as an available Jarvis app/tool route like GitHub, Gmail, Calendar, Drive, Supabase, Airtable, Playwright, OpenClaw, and other approved connectors.
- Lovable must be visible in the Jarvis app/tool stack.
- Lovable must be selectable/routable by Jarvis when the Commander asks for UI prototyping, HUD creation, public website concepting, mobile view exploration, or controlled app surface design.
- Lovable must not be treated as absent, future-only, imaginary, optional-in-theory, or outside the Jarvis command stack.
- Lovable availability does not make Lovable source of truth.
- Lovable availability does not bypass policy, privacy, GitHub, PostgreSQL, validators, or Commander approval.

## 2. What "available like other apps" means

Available means Jarvis recognises Lovable as an installed/approved app route inside the Commander tool stack.

It means Jarvis can say:

"Commander, Lovable is available as a controlled UI prototyping route. I can prepare a safe prompt, route the concept, review the output against Kingsmen doctrine, and require repo translation before implementation."

It does not mean:

"Lovable controls Jarvis."

It does not mean:

"Lovable output is production-ready."

It does not mean:

"Lovable can receive private records."

It does not mean:

"Lovable replaces GitHub."

Availability means routing capability under Jarvis control.

## 3. Required Jarvis behaviour

When the Commander says:

"Lovable next"

Jarvis must understand that Lovable is an available app route and must not act like Lovable is unavailable.

When the Commander says:

"Use Lovable for this HUD"

Jarvis must prepare a safe Lovable route plan:

- confirm the UI objective,
- prepare redacted prompt requirements,
- include Kingsmen HUD doctrine,
- include Commander-only boundary,
- include central orb, voice state, agent stack, evidence drawer, source confidence, memory panel, approval modal, command queue, and mobile Commander view,
- block secrets and raw candidate data,
- mark the output as prototype evidence,
- require GitHub translation for implementation,
- require validators for proof.

Jarvis must not respond:

"Lovable is not available."

Jarvis must not respond:

"I can only discuss Lovable theoretically."

Jarvis must not respond:

"Lovable is outside the tool stack."

Those answers violate this correction.
