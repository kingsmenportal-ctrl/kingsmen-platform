Candidate evidence, identity assurance and reviewer accountability

Document Vault & identity review readiness

Documents and identity evidence must be handled as protected candidate records. Kingsmen's intended Document Vault requires private storage, candidate-scoped access, integrity checks, human review and a complete audit trail. A file upload alone never proves identity or eligibility.

Public-site boundary: This page is a readiness standard, not the authenticated Document Vault. This public site does not accept file uploads, store identity documents, verify identity or create reviewer decisions. Checklist flags are stored only in this browser and are not sent to Kingsmen. Do not upload or paste ID documents, passports, certificates, results, CVs or private evidence here.

Document acceptance and protection standard

Accepted formats

Allow-listed file types

PDF, JPEG and PNG only: application/pdf, image/jpeg and image/png. Validate actual file content and signatures server-side; never trust a filename or browser-supplied MIME type. Reject executable, archive, macro-enabled and unrecognised formats.

Maximum size

10 MiB per file

Enforce the limit at the application boundary and storage layer. Return clear rejection reasons without exposing internal storage paths or implementation details.

Integrity

SHA-256 fingerprint

Calculate SHA-256 server-side after upload and retain the digest with document metadata so stored objects can be checked for accidental change or mismatch.

Storage

Private object storage

Store files in non-public private object storage under opaque keys. No public bucket, predictable object path or permanent public document URL.

Access

Expiring signed URLs

Issue short-lived, purpose-limited expiring signed URLs only after authorisation. Re-check candidate ownership or reviewer assignment before every view and download.

Inspection

Safe review pipeline

Validate file signatures, enforce size and format, malware-scan before reviewer access, quarantine unsafe files and avoid rendering untrusted content in privileged contexts.

Candidate document journey

Explain purpose and obtain consent

Explain why a document is needed, who may review it, retention, correction and deletion. Collect only information necessary for the stated purpose.

Upload through the authenticated portal

Verify the signed-in candidate. Enforce PDF/JPEG/PNG and 10 MiB limits on the server. Public information pages must never handle private uploads.

Validate, scan and fingerprint

Check actual file type, size, integrity and malware result. Calculate a SHA-256 digest. Keep document contents out of ordinary application logs.

Store privately and confirm receipt

Store under a non-public key and show a receipt/status. An upload receipt is not identity verification, eligibility approval or a provider outcome.

Review and allow correction

An authorised human reviewer records a decision or requests a replacement with a specific reason. The candidate can see the request and submit corrected evidence.

Retain or delete under policy

Use a documented retention schedule, justified legal hold where required, secure deletion and an auditable record. Do not retain files indefinitely by default.

Identity review state model

Candidate-visible states

Not provided

No identity evidence submitted.

Uploaded — awaiting review

The system received a file. Identity is not yet verified.

In review

An authorised reviewer is assessing evidence.

Correction requested

The candidate receives a reason and may submit corrected evidence.

Verified or not verified

A human reviewer records the decision, reason, evidence reference and timestamp.

Reviewer controls

  • Require authenticated reviewer identity and an explicit reviewer role.
  • Scope access to assigned cases and the minimum documents needed.
  • Record evidence checked, decision, reason, reviewer ID and timestamp.
  • Prevent reviewers from approving their own identity or bypassing policy.
  • Provide a documented correction and appeal path.
  • Keep candidate-level identity verification distinct from approval of an individual file.

Reviewer approval is human-controlled. AI/Jarvis may assist with classification, completeness checks or anomaly flags, but must not autonomously approve identity, alter permissions or decide eligibility. Founder approval is required for privileged policy changes and release gates.

Security, privacy and audit acceptance criteria

Isolation and authorisation

  • Candidate A must not read Candidate B's document metadata, files, signed links or review history.
  • Test reciprocal Candidate A/B access denial with authenticated sessions.
  • Reviewers access only cases within their authorised assignment.
  • Enforce access in backend and storage policies, not merely client-side visibility.
  • Keep service-role credentials server-side and out of browser bundles.

Audit and lifecycle

  • Audit upload, validation, scan, view, download, correction, decision, replacement and deletion.
  • Protect audit entries from ordinary candidate or reviewer modification.
  • Minimise sensitive content in logs; record event metadata and references instead.
  • Apply expiry, deletion and legal-hold rules to metadata and private objects consistently.
  • Test encrypted backup and isolated restore parity for files, metadata and audit history.
