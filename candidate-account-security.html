Identity, access and candidate protection

Candidate identity & account security

One candidate account must resolve to one verified candidate identity. Every protected read or write must derive ownership from the authenticated user and a verified database link—not from a candidate ID supplied by a browser, profile field, email address or untrusted token claim.

Public-site boundary: This page documents Kingsmen's security and release requirements. It is not a registration, login, password-reset or identity-verification service. Do not enter credentials, OTPs, identity numbers, recovery codes or personal documents here. The checklist saves only completion flags in this browser and is not sent to Kingsmen.

Canonical candidate identity model

Identity source

Verified account binding

The authenticated Supabase user is resolved through the protected candidate_auth_identity_links mapping. A binding is authoritative only when its status is VERIFIED, its verification timestamp is valid and its verifier evidence is present.

Uniqueness

One-to-one relationship

PostgreSQL uniqueness must prevent one candidate from linking to multiple Supabase users and one Supabase user from linking to multiple candidates. Enforce both constraints in the database, not only in application code.

Ownership

Derive from auth.uid()

Candidate ownership is derived server-side from the authenticated caller. Do not trust a candidate ID from request paths, query parameters, editable profile metadata, email matching or caller-controlled app metadata.

Failure mode

Fail closed

Missing configuration, invalid tokens, no verified link, duplicate links, expired evidence, RPC errors or ownership mismatch must deny access. Never use a service-role fallback to rescue a failed identity check.

Candidate onboarding and account lifecycle

Register and verify contact

Create the authentication identity through the approved registration flow and verify the email address. Email remains the primary Kingsmen communication route; WhatsApp/SMS are not assumed to be enabled.

Collect consent and establish candidate identity

Explain the purpose of profile and identity processing, collect required consent, minimise fields and start the identity-linking process. Email similarity alone is not identity proof.

Verify and link through an authorised process

An authorised process checks the candidate record, prevents duplicate bindings and records verifier, timestamp and supporting evidence. A link becomes authoritative only after it is verified.

Resolve every session to the verified candidate

Validate the Supabase bearer token, then resolve exactly one verified candidate identity from the caller-scoped database function. Reject missing, multiple or unverified links.

Apply account state and session policy

Only ACTIVE accounts may access protected candidate workflows. Pending, locked, disabled or recovery-required accounts follow restricted states.

Audit changes and provide recovery

Record account creation, verification, linking, unlinking, lockout, recovery and privileged changes. Recovery must verify control of the approved channel and must not silently create a new candidate identity.

Authorization rules for every protected route

Allowed authorization sequence

  1. Require a bounded, well-formed bearer token.
  2. Validate the token with Supabase Auth.
  3. Use the public anon key and caller bearer token for the user-scoped identity lookup.
  4. Resolve exactly one verified candidate link derived from auth.uid().
  5. Check the requested resource belongs to that candidate.
  6. Apply database RLS and resource-specific permissions before returning data.

Timeouts, malformed responses, network errors or uncertain ownership deny the request.

Forbidden authorization shortcuts

  • Accepting candidate_id from a client as proof of ownership.
  • Using email, display name or editable profile metadata as the identity join.
  • Using caller-controlled JWT app_metadata as candidate authority.
  • Directly exposing the identity-link table to anon or ordinary authenticated reads.
  • Using a service-role fallback after a caller-scoped identity check fails.
  • Returning candidate data before checking resource ownership.

Session, device trust and recovery states

Session safeguards

  • Generate unpredictable server-side session identifiers using cryptographic randomness.
  • Require explicit timezone in expiry timestamps and reject malformed or expired values.
  • New sessions start UNTRUSTED; a client-provided device fingerprint does not establish trust.
  • Promote device trust only through a separate server-side verification process.
  • Apply session expiry, revocation and recovery controls with audit events.

Account status behavior

  • PENDING: registration or verification incomplete; restricted access.
  • ACTIVE: eligible for protected workflows after identity resolution.
  • LOCKED: deny protected access and require controlled recovery.
  • RECOVERY_REQUIRED: restrict access until recovery checks pass.
  • DISABLED: deny login and protect retained records under policy.

Isolation, reviewer controls and POPIA evidence

Candidate A/B isolation

Candidate A must be denied Candidate B's profile, applications, documents, identity state, signed links and audit history. Run reciprocal A-to-B and B-to-A tests against the actual API, RLS and Storage permissions.

Reviewer authorisation

Reviewers require a distinct authenticated role, assigned scope and recorded reason for access. Candidate users cannot assign reviewers or approve their own identity.

Consent and data lifecycle

Record consent purpose and version, retention basis, access/deletion requests, data minimisation and auditable processing. Restrict sensitive identity evidence to the smallest authorised group.

Founder and Jarvis governance

AI/Jarvis may assist with checks and summaries but cannot approve identity, alter ownership or bypass security gates. Privileged policy changes and production release require human/founder approval.
